Viva & Demonstration Guide (Table 2)
(a) Vulnerable Implementation

Located in app.py within function sqli_auth():

# String formatting concatenates raw user input into SQL syntax query = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'" cursor.execute(query)
(b) Working Exploit Payload

In the username field, input:

admin' --

Resulting executed SQL query on server:
SELECT * FROM users WHERE username = 'admin' --' AND password = '...'
The -- comment sequence instructs the SQLite engine to discard all subsequent syntax, short-circuiting the password verification.

(c) Root Cause

Lack of separation between data and control: User input contains characters (single quotes and comment markers) that are interpreted by the database engine as SQL language commands rather than literal string data, altering query semantics.

(d) Mitigation Implemented

Parameterized Queries (Prepared Statements): Query structure is pre-compiled by the database engine; parameters are passed strictly as literal values through positional placeholders (?).

query = "SELECT * FROM users WHERE username = ? AND password = ?" cursor.execute(query, (username, password))
(e) Other Mitigations from Lecture (Theory)
  • Input validation with allow-lists: Enforcing strict alphanumeric constraints (e.g. ^[a-zA-Z0-9_]{3,30}$) ensures disallowed characters (', ;, -) are rejected upfront.
  • Least-privilege database accounts: Running web application database connections under restricted accounts with limited permissions prevents administrative tables from being altered or queried.
  • Safe errors (generic error handling): Suppressing verbose SQL database error messages prevents error-based reconnaissance by attackers.
  • Password hashing: Storing salted hashes (e.g., bcrypt/Argon2) rather than plain-text prevents direct password comparison logic flaw.
